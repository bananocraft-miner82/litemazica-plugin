# Litemazica plugin

A Spigot/Paper/Purpur plugin that builds [Litemazica](https://litemazica.app) mazes
directly into your world from a share code, and can reset them on a schedule.

It's a thin client: the maze is generated by the Litemazica API (the same engine
as the web app), returned as a `.litematic`, and placed by the plugin. No maze
logic is duplicated here. It can also build directly from a `.litematic` file you
drop in its schematics folder — no API call — see
[Local schematics](#local-schematics-litemazica-place).

## Supported servers

| Platform | Artifact | Versions |
| --- | --- | --- |
| Spigot / Paper / Purpur | `Litemazica.jar` | **1.20 and newer — one jar for all of them** |
| Fabric (server-side) | `Litemazica-fabric-mc<version>.jar` | one jar **per** Minecraft version |
| NeoForge (server-side) | `Litemazica-neoforge-mc<version>.jar` | one jar **per** Minecraft version |

The **Bukkit plugin** uses no NMS or server internals, so it doesn't need
per-version builds. It compiles against the *oldest* API it supports (Spigot
1.20.1); Bukkit keeps old methods around, so that jar runs on later servers too.
CI re-compiles the same source against 1.20.1, 1.20.6, 1.21 and 1.21.4 to keep
that claim honest.

The floor is 1.20 because block rotation (`BlockData.rotate`) — what keeps
stairs, torches and chests facing the right way when a maze is rotated to your
facing — doesn't exist before it.

The **mods** cannot work that way. Fabric and NeoForge compile against
Minecraft's own classes, which are renamed every release, so a mod built for
1.20.1 will not load on 1.21. Mod jars are therefore built per Minecraft version
and named accordingly. NeoForge additionally only exists for 1.20.2+, and its
tooling needs Java 21, so its default target is 1.21.1 rather than 1.20.1.

Neither loader has a permission system, so the Bukkit permission split maps onto
vanilla op levels: `start` is available to everyone, every other subcommand
requires op level 2.

The two mods share all their logic through `core` but not their source: Fabric
uses Yarn mappings and NeoForge uses Mojang mappings, so the same call is spelled
differently in each (`ServerWorld` vs `ServerLevel`, `BlockRotation` vs
`Rotation`). Each adapter is about 300 lines; everything below it is shared.

## Layout

A Gradle multi-module build, so the same logic can back several server platforms:

| Module | What's in it |
| --- | --- |
| `core` | Everything the plugin does, minus the bits that must touch a server: API client, NBT reading, schematic decoding, placement, terrain snapshots, regeneration scheduling, persistence. **No Minecraft dependency at all** — and none may be added. |
| `bukkit` | The Spigot/Paper/Purpur adapter: implements the platform interfaces, plus the command layer. |
| `fabric` | The Fabric server-side mod: the same interfaces over `ServerWorld`, plus a Brigadier command layer. |
| `neoforge` | The NeoForge server-side mod: the same again over `ServerLevel`, in Mojang mappings. |

About 70% of the code sits in `core`, and all 180 unit tests run there — no server
needed. A new platform (Fabric, NeoForge) implements a handful of interfaces in
`app.litemazica.core.platform` and supplies a command layer; it does not
re-implement placement, snapshots or scheduling.

| Interface | What the platform must provide |
| --- | --- |
| `WorldAccess` | read/write blocks, list and capture/restore block entities, apply loot tables |
| `Scheduler` | run a slice each tick, hop on/off the main thread, a repeating timer |
| `PlayerLookup` | who is inside a region, and teleporting |
| `Audience` | send a message with an intent (info/success/warning/error) |
| `ConfigSource` | typed settings lookup |
| `Platform` | ties the above together with a logger and a data folder |

Blocks cross that boundary as block-state **strings**
(`"minecraft:oak_stairs[facing=east]"`), which Bukkit parses with
`createBlockData` and vanilla with `BlockArgumentParser` — so `core` never needs
a platform block type. Block entities cross as opaque byte blobs, which lets
Bukkit use its per-type workaround while a mod can pass real NBT.

## Build

Requires JDK 17 or newer; the Gradle wrapper handles Gradle itself.

```bash
./gradlew build
```

Artifacts:

| File | For |
| --- | --- |
| `bukkit/build/libs/Litemazica.jar` | Spigot/Paper/Purpur `plugins/` |
| `fabric/build/libs/Litemazica-fabric-mc<version>-<v>.jar` | Fabric `mods/` |
| `neoforge/build/libs/Litemazica-neoforge-mc<version>-<v>.jar` | NeoForge `mods/` |

The mod modules need a JDK 21 toolchain; Gradle downloads one automatically if
you don't have it.

To build a mod against a different Minecraft version:

```bash
./gradlew :fabric:build -PminecraftVersion=1.21.4 -PyarnMappings=1.21.4+build.8 -PfabricApiVersion=0.114.0+1.21.4
```

```bash
./gradlew :neoforge:build -PneoForgeVersion=21.4.140 -PneoMinecraftVersion=1.21.4
```

## Tests

```bash
./gradlew test
```

Unit tests cover the pure logic: placement geometry (entrance anchoring and
rotation), region maths, regeneration scheduling, id minting, name rules, the
chunked snapshot capture/restore round-trip (over a fake world), the blend/
terrain classifiers, and Litematica bit-unpacking. Anything that needs a live
server — actual block placement, loot, scheduling in situ — is covered by the
checklist in [TESTING.md](TESTING.md).

To check the source still builds against a different Spigot API version:

```bash
./gradlew :bukkit:compileJava -PspigotApiVersion=1.21.4-R0.1-SNAPSHOT
```

## Releasing

Releases are cut by tag. Pushing a `v*` tag builds every artifact in parallel,
then publishes a single GitHub Release with all of them attached:

```bash
git tag v1.0.0 && git push origin v1.0.0
```

The workflow builds with `-Pversion=<tag>`, which flows into `plugin.yml`,
`fabric.mod.json` and `neoforge.mods.toml`, so the in-game version matches the
release. `Release` can also be run manually from the Actions tab, supplying the
version, if you need to re-cut one.

### What gets published

| Server | Asset | Per Minecraft version? |
| --- | --- | --- |
| Spigot / Paper / Purpur | `Litemazica-bukkit-<version>.jar` | No — one jar covers 1.20+ |
| Fabric | `Litemazica-fabric-mc<mc>-<version>.jar` | Yes |
| NeoForge | `Litemazica-neoforge-mc<mc>-<version>.jar` | Yes |

### The Minecraft version matrix

Which Minecraft versions the mods are built for lives in
[`mc-targets.json`](mc-targets.json) — one file, read by both CI and the release
workflow to generate their build matrices. Adding a version is a single edit
there; no workflow changes.

It is not always free, though. The mod loaders compile against Minecraft's own
classes, so a new series can break the adapter — going from 1.20.1 to 1.21.1
changed four calls (block-entity NBT needing registry access, `NbtIo` needing a
size tracker, and loot tables moving from `Identifier` to `RegistryKey`). All
four were in a single class.

That's why the Fabric module keeps its one volatile class in a per-version
source directory:

```
fabric/src/main/java/     shared: entrypoint, platform, audience, commands
fabric/src/mc1.20/java/   FabricWorldAccess for 1.20.x
fabric/src/mc1.21/java/   FabricWorldAccess for 1.21.x
```

The build picks the directory matching the target's version series, so adding a
series means adding `src/mc<series>/java` with the class that drifted — not a new
module. CI builds every target on every pull request, so a break shows up
immediately rather than at release time.

## Install

**Bukkit / Paper / Purpur**

1. Drop `Litemazica.jar` into your server's `plugins/` folder.
2. Start the server once to generate `plugins/Litemazica/config.yml`.
3. Set `api-base-url` (see below), then `/litemazica reload` or restart.

**Fabric**

1. Install Fabric Loader and the Fabric API mod on your server.
2. Drop the matching `Litemazica-fabric-mc<version>.jar` into `mods/`.
3. Start the server once to generate `litemazica/config.properties` in the game
   directory (same keys as below, in properties form), then `/litemazica reload`.

**NeoForge**

1. Install NeoForge on your server (21.1+ / Minecraft 1.21.1+).
2. Drop the matching `Litemazica-neoforge-mc<version>.jar` into `mods/`.
3. Start the server once to generate `litemazica/config.properties`, then
   `/litemazica reload`.

## Configuration (`config.yml`)

| Key | Default | Meaning |
| --- | --- | --- |
| `api-base-url` | `https://litemazica.app` | Base URL of the Litemazica API. |
| `request-timeout-seconds` | `20` | HTTP timeout for a generate request. |
| `schematic-folder` | `schematics` | Folder (under the data folder) where admins drop `.litematic` files for `/litemazica place`. Created on first run. |
| `max-volume` | `6000000` | Refuse to place a maze larger than this many blocks. |
| `snapshot` | `true` | Record the terrain under a maze so `remove` puts it back. |
| `snapshot-max-volume` | `6000000` | Skip the snapshot above this many blocks; `remove` then clears the maze to air. Snapshots are per-chunk files streamed a chunk at a time, so memory stays flat regardless of size — this cap is only about disk and background capture/restore time. The default matches the largest buildable maze, so every maze is restorable by default. |
| `blend-top-reach` | `0` | Blend an **open-top** maze into the terrain above: scan this many blocks up, stripping canopy/water under open sky and capping under rock/dirt (~40 is a good "on" value). The editor's per-maze "Blend top" toggle wins; this fallback applies only to mazes with no ceiling. All changes are snapshotted, so `remove` restores them. |
| `default-regen-minutes` | `0` | Regen interval a new maze starts with (0 = off). |
| `regen-fresh-layout` | `true` | New maze layout on reset (`true`) or the same one (`false`). |
| `regen-check-seconds` | `30` | How often the scheduler checks for due resets. |
| `editor-poll-seconds` | `4` | How often `/litemazica editor` polls for a pressed Apply. |

> The `?seed=` / `?reset=off` overrides the plugin relies on for regeneration,
> and the `/api/editor/*` endpoints behind `/litemazica editor`, live in the
> Litemazica Worker. If you point `api-base-url` at your own deployment, deploy a
> build that includes them (and run its D1 migrations).

## Commands

Permissions are `litemazica.<start|editor|edit|generate|place|files|list|remove|regen|reload>`,
or `litemazica.*` for all of them.

`litemazica.start` defaults to **everyone** — playing a maze isn't an admin
action. Every other node defaults to **op**. Revoke `litemazica.start` in your
permissions plugin if you want to gate entry behind a rank.

| Command | Permission | Does |
| --- | --- | --- |
| `/litemazica editor` | `editor` (op) | Open the web editor, design a maze, and build it where you stand by pressing **Apply** — no code to type. |
| `/litemazica edit <id>` | `edit` (op) | Re-open a placed maze in the web editor with its current design loaded; **Apply** rebuilds it in place. API mazes only. |
| `/litemazica start [id]` | `start` (all) | Teleport yourself to a maze entrance, facing in. |
| `/litemazica generate <code> [x y z] [name]` | `generate` (op) | Build a maze with its entrance at your feet (or at `x y z`), facing the way you look. Optionally name it. |
| `/litemazica place <file> [x y z] [name]` | `place` (op) | Build a maze from a `.litematic` in the schematics folder, anchored and facing like `generate`. |
| `/litemazica files` | `files` (op) | List the `.litematic` files available to `place`. |
| `/litemazica list` | `list` (op) | List placed mazes with their region and regen settings. |
| `/litemazica remove <id>` | `remove` (op) | Remove a maze and restore the terrain it was built over. |
| `/litemazica regen <id> <off\|hourly\|daily\|weekly\|monthly> [fresh\|same]` | `regen` (op) | Set a maze's reset schedule. |
| `/litemazica regen <id> now [fresh\|same]` | `regen` (op) | Reset a maze immediately. |
| `/litemazica reload` | `reload` (op) | Reload `config.yml`. |

Aliases: `/litemaze`, `/lmz`, `/maze`.

### Local schematics (`/litemazica place`)

Besides fetching from the API, the plugin can build a maze from a `.litematic`
file you drop in the schematics folder (`plugins/Litemazica/schematics/` on
Bukkit; `litemazica/schematics/` on Fabric/NeoForge — created on first run).
Run `/litemazica files` to see what's there, then
`/litemazica place <file> [x y z] [name]`. The file is read straight off disk —
no conversion step, and no API call.

A hand-made file carries none of the placement metadata the API sends, so:

- **Entrance / orientation.** The entrance defaults to the middle of the
  schematic's north (`z=0`) edge at floor level, and the whole structure is
  rotated to face you (or the way you look at `x y z`) — exactly like `generate`.
- **Reset means restore, not reshuffle.** A file has no generator behind it, so
  a scheduled reset (or `/litemazica regen <id> now`) rebuilds the *same* layout:
  it re-rolls loot chests and undoes anything players dug through. `fresh` is
  ignored for file mazes.
- **First region only.** A multi-region `.litematic` places its first region; the
  rest are skipped with a warning in the log.
- **Chests.** Containers fill from **loot tables** (re-rolled on every reset).
  Items placed literally in a chest in the schematic are not written — give the
  container a loot table if you want it to fill.
- **Trapped-chest bait.** A trapped chest emits redstone when opened; wire that in
  the schematic to TNT or dispensers. At placement each trapped chest is a coin
  flip: half stay live (**armed** — opening springs the wired trap) and half are
  swapped for a plain chest (**decoy** — safe to open), keeping their facing and
  loot either way. Re-rolled on every reset, so players can't learn which chests
  bite.
- **Dispenser traps.** Placement writes the dispenser block but no contents, so
  each trap dispenser is then stocked from the **schematic's own baked ammunition**
  — the web-app editor's seed-deterministic mix of plain/spectral/tipped arrows and
  splash/lingering-potion charges. The plugin reads and applies those exact items
  (rebuilding them for the running server's item-NBT form as needed); it does *not*
  invent its own, so a dispenser fires the same load every reset. A dispenser with
  nothing baked in is left as placed.
- **Spawner rooms.** Placement writes the (empty) spawner block; the plugin then
  arms it with the **mob the schematic baked in** (the web-app editor's
  seed-deterministic choice, read from `SpawnData` in either the flat pre-1.18 or
  nested 1.18+ form) on a fixed vanilla cadence. The same monster every reset —
  the plugin applies the baked mob rather than picking its own. The darkness is
  authored in the schematic (leave the room unlit); a spawner with no baked mob is
  left as placed.
- **Randomised pressure plates.** Lay a field of **heavy (iron) weighted pressure
  plates** over hidden dispensers or TNT: at placement about half are cleared to
  air so the live tiles — and the safe path across the field — shuffle, re-rolled
  on every reset. Only that one plate type is a trap marker; every other pressure
  plate is décor and is left exactly as placed.
- **Cross-version blocks.** A block id or state the running server doesn't know is
  placed as air and logged, rather than failing the build.

### Tab completion

Every argument completes to something. Where there are real values it offers
them — placed maze ids, interval names, `fresh`/`same`, `confirm` — filtered by
what you've typed so far and by your permissions.

Where there's nothing concrete to offer it names the argument instead, so the
prompt is never blank: `<litemazica-code>`, `<maze-id>`, `<name>`. `place`
completes its first argument to the **actual `.litematic` files** in the
schematics folder. The coordinates on `generate` and `place` suggest **your own
position**, so tabbing through the code/file and then the coordinates fills in
where you're standing.

Placeholders avoid spaces deliberately — the client splits completions on
whitespace, so `<litemazica code>` would insert as two arguments.

On Fabric and NeoForge this comes from Brigadier, which shows argument names and
validates types natively.

## The web editor (`/litemazica editor`)

`/litemazica editor` is the easiest way to build a maze, and it sidesteps
Minecraft's 256-character chat limit entirely — you never type or paste a code.

1. Run `/litemazica editor`. The plugin opens a short-lived session and sends you
   a clickable link.
2. Design your maze in the browser as usual, then press **Apply to server**.
3. The plugin — which has been polling that session — builds the maze **where you
   are standing at that moment**, exactly like `/litemazica generate` at your feet.

Sessions last up to an hour and are one-per-player (running it again replaces the
old one). Leaving the server, or letting the session expire, cancels it. The
handshake is a token stored server-side by the Litemazica API; the code travels
browser → API → plugin over HTTP, so its length never matters.

> This is the recommended path when a code would be long — a custom mask or a
> heavily-tweaked config can exceed what chat will accept if pasted directly.

### Re-editing a placed maze (`/litemazica edit <id>`)

`/litemazica edit <id>` re-opens an existing maze in the browser **with its
current design loaded**, so you can tweak it and rebuild it in place:

1. Run `/litemazica edit <id>`. The plugin opens an editor session seeded with
   that maze's share code, so the editor starts on its exact settings.
2. Change whatever you like, then press **Apply to server**.
3. The plugin rewrites maze `<id>` **at its existing anchor and facing** — no new
   maze, no teleport. If the edited footprint differs, the original terrain is
   restored underneath first and re-snapshotted, so a later `remove` still cleans
   up. The maze's stored design is updated too, so scheduled resets reproduce the
   edited layout.

Only mazes built from the API/editor can be re-edited — a maze placed from a
local `.litematic` (`/litemazica place`) has no editable design, so edit that
file and place it again instead. The maze must be idle (not mid-reset) and empty
of players, same as a regeneration.

> Requires the web app to support seeding a session — the Worker embeds the
> maze's code in the editor URL as `?s=`. If you self-host, deploy a build that
> includes it (see the Litemazica web app repo).

## Naming a maze

A maze can be named when it's built, and the name *is* its id — so every command
takes it:

```
/litemazica generate <code> arena
/litemazica generate <code> 100 64 100 arena
/litemazica start arena
/litemazica regen arena daily fresh
/litemazica remove arena
```

Without a name, mazes get `m1`, `m2`, and so on.

Names may contain letters, digits, hyphens and underscores, up to 32 characters.
They can't be **only digits** — otherwise `generate <code> 100 64 100` couldn't
be told apart from a maze named `100`. That's also how the optional coordinates
and the optional name stay unambiguous: three integers are coordinates, and a
trailing non-numeric argument is the name.

Lookups ignore case, so `/litemazica start ARENA` finds `Arena`. Names must be
unique (also ignoring case), and that's checked before the maze is fetched, so a
clash costs you nothing.

## Entering a maze

`/litemazica start` drops you at the entrance, standing on the threshold and
facing down the first corridor — the plugin stores the entrance position and
facing when the maze is built, so this is exact rather than approximate.

The id is optional when only one maze is placed. With several, it lists them and
asks which. It refuses while a maze is mid-reset, so nobody lands inside a
half-built maze; and once you're in, you count as "inside the region", so a
scheduled reset defers until you leave.

## Removing a maze

Before a maze is built, the plugin records the terrain it's about to cover, so
`/litemazica remove <id>` puts the world back rather than leaving a box of air.
Each snapshot is a folder, `plugins/Litemazica/snapshots/<id>/` — a small
manifest plus one gzipped file per world chunk it covers. It's **captured and
restored one chunk at a time**, so only a single chunk is ever held in memory:
the snapshot's size is bounded by disk, not RAM, no matter how large the maze.
The folder is deleted once the terrain is restored.

Captured: every block, plus chest/barrel contents, sign text, spawners and loot
tables. **Not** captured: entities such as item frames, armour stands and
paintings — placement doesn't delete those, but a restore won't bring them back
either. Anything built *inside* the region after the maze went in is overwritten.

If there's no snapshot — because `snapshot` is off, the region exceeded
`snapshot-max-volume`, or the maze predates this feature — `remove` falls back to
clearing the region to air and says so.

## How a maze meets the terrain

By default placement stamps the maze's whole bounding box over the world, air
included — that's what guarantees clean, empty corridors. Two conventions let a
maze blend into surrounding terrain instead:

- **Keep the ground under a maze (`structure_void`).** A basement layer full of
  `minecraft:structure_void` is *skipped* at placement, leaving the original
  terrain in place, while real `air` still carves through. So drop-trap shafts
  (authored as air) cut down into the ground, but the earth around them isn't
  hollowed into a void. The Litemazica editor emits `structure_void` filler for
  this automatically; hand-made schematics can use it too.
- **Blend an open-top maze into the terrain above.** A maze with no ceiling can
  sit under trees or a hillside. With "Blend top" on (the editor toggle, or
  `blend-top-reach`), the plugin/mod reads the world above each column and adapts:
  - **Over the open top** it clears ground cover (grass, water, snow, flowers, leaf
    litter) *and* any lone floating solid layer — a one-block dirt/grass shelf that
    would otherwise hang over a corridor is removed along with anything on it
    (capping a single layer would just leave an isolated patch of ceiling). Any tree
    whose wood stands over the maze is **felled**: a flood-fill follows its *logs*
    (trunk and branches) and breaks each with a neighbour update, exactly like a
    player cutting it down, so vanilla's leaf-decay clears the canopy it supported.
    Leaves are never edited directly — so a neighbouring tree, still supported by its
    own untouched trunk, keeps its canopy and isn't decapitated. The blend only
    touches columns over the maze proper, never the `structure_void` margin ring the
    schematic reserves around it.
  - **Under rock/dirt** (a solid slab ≥2 blocks thick within ~20 blocks) it caps
    every buried corridor with the ceiling material as a clean, uniform roof, and
    leaves the natural ground above — hill, surface, and any trees on it —
    **untouched**. The roof tucks one block out under the surrounding terrain so it
    reads as terrain-over-ceiling rather than ending flush at the wall, and a gap the
    open-top layout can leave between the wall top and the roof is closed so the wall
    meets the ceiling.

  Everything the blend changes is inside the maze footprint plus a small skirt and
  the band above it — exactly what the terrain snapshot covers — so `remove` puts
  the trees back and takes the ceiling caps away, restoring the world as it was.

## How regeneration works

Schedules are named: `hourly`, `daily`, `weekly`, `monthly`, or `off`. A maze
resets when the interval has elapsed **and no player is inside its region** — if
someone's in the maze, the reset is deferred to the next check, silently, and
retried. `fresh` rolls a new layout (a new seed in the same footprint); `same`
rebuilds the identical maze.

`/litemazica regen <id> now` resets a maze on the spot without changing its
schedule. A `fresh`/`same` argument there applies to that one run only. An
immediate reset obeys the same rule as a scheduled one — if anyone is inside, it
is **refused** and names who.

A bare number of minutes is also accepted in place of a preset
(`/litemazica regen m1 5`), which is handy for exercising the scheduler without
waiting an hour.

## Who can be where

Anything that rewrites blocks refuses to run over a player, and says who is in
the way:

| Action | Rule |
| --- | --- |
| `generate` | Refused if anyone is standing in the region the maze would occupy. You are exempt when building at your own feet — the entrance opens where you stand — but not when you pass explicit coordinates. |
| `regen … now` | Refused if anyone is inside the maze. |
| scheduled reset | Skipped silently while anyone is inside; retried at the next check. Re-checked again after the maze is fetched, in case someone walked in meanwhile. |
| `remove` | Warns and requires `confirm` if anyone is inside. |
| `start` | Refused while the maze is mid-reset. |

Placed mazes and their schedules are saved to `plugins/Litemazica/mazes.properties` and
restored on restart.

A `fresh` reset can shift the footprint slightly (a new seed moves the entrance
within the grid, and the entrance stays pinned to the same world position). When
that happens the plugin restores the original terrain, re-snapshots the new
footprint, and then builds — so removing the maze later still restores cleanly.
